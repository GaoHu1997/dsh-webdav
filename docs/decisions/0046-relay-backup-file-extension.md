# 0046 — 转发文件资源统一补 `.prop` 扩展名并透传额外请求头

- 状态：`已废弃（被 0050 取代）`
- 日期：2026-10-20
- 相关：[0041](0041-relay-reuses-sync-config.md)（复用同步配置与额外请求头）、[0034](0034-extra-request-headers.md)（额外请求头格式）、[0044](0044-relay-propfind-collection-slash.md)（集合基路径规范化）

## 背景

本机转发供其他 WebDAV 客户端复用现有上游服务器、账号和额外请求头。部分客户端或上游存储只接受以 `.zip` 或 `.prop` 结尾的备份文件名；客户端提供无扩展名的文件资源路径时，原样转发会导致上传不兼容。上传路径若被改名，后续读取、检查和删除也必须映射到同一个远端资源。集合路径则不能当文件名补扩展名。

## 决策

- 继续使用既有头合并规则：配置中的 `headers` 随每个请求发送；客户端协议头同名时优先；本地 `Authorization` 仅用于转发认证，上游认证仍由同步配置提供；`Host` 与逐跳头不透传。
- 对没有 `.zip` 或 `.prop` 后缀的文件资源路径，在最终路径段补 `.prop`；已有两种后缀（不区分大小写，判断时识别 URL 编码的句点）原样保留其编码形式。映射应用于文件资源的上传及后续访问，使相同的客户端路径始终指向同一个上游文件。
- 不改写 `MKCOL`、`OPTIONS`、以 `/` 结尾的集合路径，以及 `Depth` 非 `0` 的 `PROPFIND` 集合请求。基路径的 `PROPFIND` 仍依 [0044] 补规范尾斜杠。无尾斜杠、`Depth: 0` 的 `PROPFIND` 按文件资源处理。
- 不读取或改写 WebDAV 响应 XML；服务器列举结果仍显示实际存储名（含 `.prop`）。不符合扩展名条件时不拒绝请求，而是统一补 `.prop`，因为自动适配比要求每个客户端自行维护文件名更容易互操作。

## 影响

- **正面**：无扩展名的上传目标能满足只接受 `.zip` / `.prop` 的文件名约束；同一路径的上传、读取和删除映射一致。
- **正面**：既有额外请求头及客户端协议头继续透传，可用于 `X-Api-Key`、`User-Agent`、`Content-Type` 等上游要求。
- **负面**：远端文件名可能与客户端原始路径不同，服务器的目录列表会显示补上的 `.prop`；无尾斜杠且 `Depth: 0` 的扩展名-less `PROPFIND` 被视作文件而非集合。
- **负面**：转发不再对文件 URL 完全保持逐字节路径透明；该行为仅针对文件资源路径，集合操作保持原样。
- **验证**：回归测试覆盖 `.prop` 补齐、`.zip` / `.prop` 保留、读写名称一致、集合方法不变，以及上传 `Content-Type` 和配置额外头抵达上游。
