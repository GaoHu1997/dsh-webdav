# 0073 损坏的状态文件移开重置，配置文件仍然报错

- 状态：已接受；把 [0027](0027-damaged-is-not-missing.md) 对 `sync-state.json` 的处理改为本条，`sync.json` 与缓存副本的部分不变
- 日期：2026-10-24

## 背景

0027 之后，`sync-state.json` 在却读不出来时 `loadState()` 抛错。动机是对的：把状态读成空的会让下一次同步按"第一次"行事，服务器的副本盖过本机。

但后果是：**每一条路由都死**。`status()` 第一步就是 `loadState()`，于是设置卡只剩一条 400 错误；同步、恢复、撤销同样全部 400。唯一的出路是用户自己找到 `.dsh-webdav-sync/` 并删掉那个文件——而报错信息只说了文件名，没说能删。一次掉电撕裂的 JSON（NTFS 只日志元数据不保数据，`writeAtomic` 此前也没有 fsync）换来的是整个插件不可用。

同时，0027 担心的"静默接管"在如今的代码里已经有对冲：无基线的同步在采纳服务器副本前会 `keepUnmerged` 把本机配置封存进 `sync/`，并在通知里说出目录（0024）。接管不再是"无声"的。

## 决策

**`loadState()` 读到损坏的状态文件时，把它改名为 `sync-state.json.corrupt-<时间戳>`，返回空状态继续工作。** 坏字节留在旁边可查；下一次同步按第一次行事，但接管前留档、通知里说明（0024 的机制兜着）。`saveState()` 的下一次写入自然写出新文件。

**`sync.json` 仍然报错**：配置持有密钥，读成默认值会把"文件坏了"变成"同步悄悄关掉了"，比一条带文件名的错误更糟。缓存副本本就按"读不出来当没有"处理（0027 原文），不变。

否决的备选：

- **维持抛错、只改报错文案教用户删文件**：把恢复动作留给用户手动做，且删错文件（删成 sync.json）的风险真实存在。
- **损坏后写一条带 error 的新状态**：`status()` 的错误展示以 `errorKey` 对齐配置，损坏时刻拿不到能匹配的 key，展示不出来，等于又绕回静默。

## 影响

- 好的一面：状态文件撕裂从"插件瘫痪、手动恢复"变成"自动降级、损失一段基线"；损坏字节保留可查。
- 代价：`undo` 指针、dismissed 签名、错误历史随旧状态一起丢。Undo 的副本本体在 `sync/` 里没丢，但指针没了——这是丢一段基线里最疼的一块，靠 0024 的留档兜底。
- 配套：`writeAtomic()` 在 rename 前对文件句柄 `sync()`、rename 后同步目录（Windows 无目录句柄可同步，跳过），从源头把撕裂的可能性压低。
