# 0085 — 只有一个零档：关闭同步挪回动作行，手动同步不再留任何后台定时器

- 状态：已接受
- 日期：2026-11-03

## 背景

用户看着「自动同步」那一排选项卡，要求删掉重复的一项，并顺手把一件更大的事说清楚了：

> 关闭同步和手动同步如果是一个，那么你需要删除一个，另外关闭/手动同步时，不要有任何后台自动跑的逻辑

两句话说的是同一件事的两面：

1. **「关闭同步」和「手动同步」对用户就是一件事** —— 都不自动跑。前者实现上根本不是区间：它清 `url` 与 `password`（[0082](0082-stopping-a-sync-in-flight.md) 的 `turnOff()`），选项卡只是用 `state.url.trim() === '' ? AUTO_OFF : ...` 把「地址为空」画成第一档。于是同一条需求在界面上有了两个入口，而其中一个还会顺手删掉服务器地址 —— 选个频率不该有这个副作用。
2. **「手动同步」下也不该有东西在后台跑**。旧实现（[0009](0009-rescheduling-auto-sync-timer.md) 要点 2）是每次 tick 都重读配置，于是没有可做的事时也要 **每 60 秒醒一次**（`wait === 0 ? 60_000 : wait`），理由是「卡片里刚打开自动同步，下一个 tick 就自己发现了，不需要重启 DSH」。代价是：一个设成「手动同步」的机器，DSH 活着期间每秒都没有、每分钟都有一次读盘 + 一次 `resolveFromEnv`，只为确认自己无事可做。卡片这半边还有 [0039](0039-the-card-says-check-and-sync-apart.md) 留下的 15 秒 `/status` 轮询（只读本机状态，但每次都会让宿主 `relay.apply` 一次）。

顺带一提，[0031](0031-card-layout-and-chinese-messages.md) 决策九的负面清单里本来就写着「『关闭同步』混在自动同步的取值里，与『手动同步』并列，语义上它是『不再有自动同步』而不是『间隔为 0』」——这次是照那条自己记下的疑虑收尾。

## 决策

**一、选项卡只剩一个零档：「手动同步」（`AUTO_MANUAL = -1`）。**

`autoOptions(t)` 现在返回 `[手动同步, 3 分钟, 15 分钟, 30 分钟, 1 小时]`，`AUTO_OFF = 'off'` 这个伪值从卡片里删掉，`value` 回到 `String(state.autoEvery)`，`onChange` 只调 `setAuto`。存进 `sync.json` 的仍是 `AUTO_CHOICES` 里那五个数，`normaliseConfig` / `configure` / `validateConfig` 的三处校验一个都不用动 —— 删掉的只是「用空地址冒充一个档位」的呈现。

**二、「关闭同步」搬回动作行，作为第七个文字按钮。** 它保留确认框（`confirmOff`）、`/off` 路由、`turnOff()`，以及 0082 那套按代次停止在途同步的机制；颜色用警告色（与「服务器覆盖本机」「本机覆盖服务器」同档）。`disabled` 只有两种情形：「这次关闭本身在跑」（`state.busy === 'off'`）与「地址和密码都已为空」（没什么可关）。**它刻意不跟随 `busy`**：同步正在跑时它必须还能按，那正是 0082 的即时停止入口 —— 落盘后自查时发现这里一开始写成了 `disabled={busy}`，会把这唯一的出口堵死，已改回按 `busy === 'off'` 判断。[0048](0048-sync-actions-are-text-buttons.md) 把这一行做成六个不带框的文字按钮之后，它本来就是一次摊开的几个动作，把「清空这台电脑的连接」放回这里，比塞进一排频率里更符合它是什么。

否决的两种做法：

- **(a) 删掉 `/off` 与 `turnOff()`，只留手动同步。** 看起来最干净，但会一并丢掉 0082 刚做的事：在途同步被立即取消、被取消的那次不写 `last`、不记 `error`。而且「现在就把落盘的密码清掉」没有别的入口 —— 空密码框在 `configure()` 里是「沿用已存的那个」（[0015](0015-password-not-carried-across-accounts.md)），不是「清掉」。
- **(b) 只留一个标签「关闭同步」，把 `-1` 改名。** 名字变了，副作用还在：选一个频率仍然会清地址。而且「关闭同步」放在选项卡里读起来仍像一个区间值，正是 0031 决策九记下的那个毛病。

**三、定时器改成事件驱动，手动态一个定时器都不排。**

`startTimer()` 的返回值从 `void` 变成 `() => void`，`apply()` 把它存进 `rearm`，`/config` 与 `/off` 两个写配置的路由在写完、应用完转发之后调它：

```ts
  // src/index.ts —— 只有真的要用时才排
  async function rearm(first: boolean): Promise<void> {
    const mine = ++generation
    clear()
    if (stopped) return
    const current = await read()
    if (stopped || mine !== generation || current === undefined) return
    const minutes = current.config.autoEvery
    if (!usable(current.config) || minutes <= 0) return
    arm(first ? FIRST_DELAY_MS : minutes * 60_000)
  }
```

- **零档 = 没有定时器**，不是「一个每分钟醒来确认自己无事可做的定时器」。`tick()` 跑完只在仍满足 `usable && minutes > 0` 时续排；配置读不出来时也不续排（读不出来就无法区分区间与手动，猜一个出来正是用户反对的那种后台循环），下一次保存会重新装。
- **保存是唯一的开关事件**：`/config` 改成 15 分钟就立刻按 15 分钟排，改回手动就立刻清掉；`/off` 清完地址顺手把待触发的那次拿掉。这替换了原来「靠 60 秒轮询发现文件变了」的机制 —— 也正是原来那个轮询存在的唯一理由。
- **`generation` 挡住乱序**：两次保存挨得很近时，先发出的那次 `read()` 可能后回来；旧读不许用自己看到的配置覆盖新读装上的定时器。`tick()` 也一样 —— 它在开头记住当时的代次，同步跑完时若代次已经变过（那段时间里卡片存了配置），就不再用自己那份旧配置续排，否则「存成手动同步」刚清掉的定时器会在这次同步结束后自己长回来。
- **首次 20 秒（`FIRST_DELAY_MS`）只用于启动**：DSH 刚起来时 profile 可能还在写，那时跑同步只会失败并留下一条 `error`。保存触发的重排直接用配置里的间隔，不额外等 20 秒。
- `unref()` 与 `ctx.effect` 不变：待触发的定时器不阻止 `dsh` 退出，插件停用时被清掉；`stopped` 在两处 `await` 之后也复查一次，卸载时正在飞的读不会在清理之后再装一个定时器。

**四、卡片的状态轮询跟着一起收：只有自动同步开着时才轮询。**

`WebdavSyncCard.tsx` 的 `watchStatus` effect 从「打开设置页就每 15 秒读一次」改成「打开设置页 **且** 已保存的 `autoEvery > 0` 才读」。手动同步时宿主没有任何东西会自己变（除了别的窗口的操作），要刷新就按标题右边那个刷新图标 —— 它本来就是同一个读取的立即执行，现在也成了手动档下的常规入口。`watchStatus` 本身（`document.visibilityState` 判断、focus/online 监听的被动重读）不动。

**五、测试跟着换了守护点。** 0009 的定时器用例原本靠「首次 20 秒内一定有 tick」；现在启动时的第一次装载要读一次配置（真实 I/O），所以 `timerBed` 先等它真的排上（`vi.getTimerCount() > 0`）再拨时钟。新增三条：`keeps no timer at all while automatic sync is by hand`（`-1` 时 `vi.getTimerCount() === 0`，拨十分钟也没有同步）、`re-arms from a save, so turning automatic sync on or off needs no poll`（`POST /config` 之后立刻有定时器、按 15 分钟等、再存回 `-1` 立刻清掉）、以及 `does not put the timer back after a save during a running attempt says by hand` —— 这条把「正在跑的那次同步跑到一半时卡片存了 `-1`」摆出来：`tick()` 开头记住当时的 `generation`，跑完发现已经变过，就不再用自己那份旧配置续排，否则保存刚清掉的定时器会在几秒后自己长回来（去掉这个判断，这条用例会红）。`relay-host.spec.ts` 里那条「启动读配置期间被 dispose 不会复活监听」原来断言 `loadConfig` 只被调一次，现在启动有两次读（转发与定时器各一次），断言改成「至少调过」，要守的行为（dispose 之后不 `apply`、端口不再监听）不变。

## 影响

正面：

- 界面上一个零档、一个动作，不再有「选个频率顺手删掉地址」这种副作用；`AUTO_OFF` 这个伪值连同 `value` 里的空地址判断一起消失。
- 「手动同步」是真的什么都不做：没有定时器、没有周期请求，`dsh` 空闲时的读盘次数从「每分钟一次」降到零。
- 打开或关闭自动同步仍然不用重启、不用刷新：保存路由当场重排。这条体验是原来那个 60 秒轮询想换来的，现在用事件换，代价更低。
- 关闭同步的能力一点没少（确认框、清地址与密码、停转发、在途同步硬停），只是位置从「频率」挪到了「动作」。

负面：

- **手改 `sync.json` 不再被自己发现**。原来「编辑文件 → 下一秒 tick 读到」是个（没写进文档的）副作用；现在只有下一次保存、下一次 tick 或重启才生效。真实用法里没有人手改它，但这个能力确实没了。
- **配置读不出来时定时器停摆**，直到下一次保存。旧实现会每分钟重试读一次，现在不猜 —— 这是刻意选择（读不出配置就无法判断该不该自动跑），代价是磁盘短暂故障会推迟自动同步，且卡片上不一定看得到原因。
- **手动同步下卡片的时间自己不动了**。两个时间戳要等按刷新图标、或者任何一个动作之后才更新；原来是每 15 秒自动重读。
- 定时器相关的测试多了一层「等首次装载完成」的等待，`relay-host.spec.ts` 的读次数断言也放宽了 —— 都是这次把「读配置」从轮询变成启动/保存事件的直接后果。以后新增写配置的路由，必须记得在里面调 `rearm()`，否则那条路由保存的间隔要等到下次别的保存或重启才生效；这是一条新的、靠人记住的约定（已写进 `startTimer` 的注释）。
- 0009 里「没事可做时按 60 秒轮询」那条设计、0031 决策九的选项卡顺序、0039 的常驻 15 秒轮询描述，都只在这篇之后的历史里成立；旧文档保留原文，各自加了指向本篇的注记。
