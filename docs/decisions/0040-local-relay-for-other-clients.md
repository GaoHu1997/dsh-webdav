# 0040 — 本机转发：把插件里的账号与请求头借给别的 WebDAV 客户端

- 后续：[0041 — 本机转发复用同步配置](0041-relay-reuses-sync-config.md)；以下保留旧设计的历史依据。
- 日期：2026-10-20
- 相关：[0034](0034-extra-request-headers.md)（额外请求头，同一套写法）、[0026](0026-password-not-in-state-key.md)（凭据只在本机用）、[0008](0008-browser-half-over-routes.md)（浏览器半边只走路由）

## 背景

用户想用这份已经填好的 WebDAV 账号去同步**别的程序**的配置。具体那个程序是 [magpie](https://github.com/yetone/magpie)：它自己有一套 `internal/davsync`，支持 WebDAV / S3 / 加密的 GitHub 仓库，但**它的备份格式与本插件不是一回事**（分片名不同、信封里 `format` 不同、`version` 不同、`KeepOwn` 那套「本机字段不上行」的规则也不同）。所以两条路都堵着：

- 让本插件把 magpie 的配置当一份来同步：要做成第一等分片（每台电脑的 magpie 目录里有 `library/`、`backups/`、`sync/` 这些又大又不该同步的东西），还得复刻 `KeepOwn` 的黑名单，工作量远大于这个需求本身。
- 让本插件直接读写 `magpie.magpie-backup`：两边的 bundle schema 不同，等于在 TypeScript 里再实现一遍 magpie 的 `backup.Collect`/`Restore`。

真正卡住的其实是一件更小的事：**magpie 那边的同步要填 WebDAV 地址、账号、密码，而且这类客户端往往没有「额外请求头」这个字段**。用户的服务器恰恰需要额外头（`User-Agent`、`X-Api-Key` 之类，见 [0034](0034-extra-request-headers.md)），而这些凭据和头都已经在本插件的配置里了。于是问题变成：**能不能让本插件把它已经知道的账号与请求头，借给本机上的另一个 WebDAV 客户端用**。

## 决策

**一、在本机起一个只绑 `127.0.0.1` 的转发器，客户端把同步地址改成它。**

客户端（magpie、任何别的 WebDAV 客户端）把地址填成：

```
http://127.0.0.1:<端口>/<32 位十六进制 token>
```

转发器把这个地址下的每个请求**原样流式转发**给配置里的真实 WebDAV 基址，只做三件事：补上配置的请求头、把响应回来、把 `Location` 改回转发地址。它**不解析 WebDAV** —— 方法、路径、请求体、`If-Match`、`Depth`、状态码、ETag 全部原样过。

被否决的备选：

- **每个客户端里各填一份账号密码与请求头** —— 最省事，但凭据被复制到 N 个程序的配置文件里（每个的落盘方式、权限、能否加密都不同），而需要额外头的客户端根本填不了头，这条路直接不成立。
- **把转发器绑在所有网卡上** —— 一行代码之差，但那是把**已经解好的凭据**开放给整个局域网。局域网里的任何设备都能拿它读写这份备份，而这份备份里有 `patch` 份（整份 `cordis.patch.yml`）。
- **在转发器里解析并重写 WebDAV 请求** —— 要走完整的 `PROPFIND`/`MKCOL`/`If-Match` 语义，等于实现半个客户端；原样透传没有失败面，客户端自己的 WebDAV 实现照常工作。
- **把 token 放进请求头而不是路径里** —— 拒绝它的理由就是转发器存在的原因：这些客户端**没有**自定义请求头的能力。

**二、token 在第一次保存时生成，此后不变；端口也一样。**

地址是客户端那边的**服务器身份**：它的同步状态（magpie 的 `sync-state.json`，本插件的 `stateKey`）都记在「地址 + 账号 + 口令」上。地址一变，客户端就以为是另一台服务器，会从「首次加入」重新开始 —— 那意味着拿服务器上的旧备份盖掉本机较新的那份。所以：

- 端口与 token 一起落盘，默认端口 `3426`（挨着 magpie 自己的网关 `3425`，好记且不撞）；
- 卡片上「换一个地址」是**显式**动作（`{ token: '' }` 才重新铸一个），平时怎么也轮不到它；
- `normaliseRelay` 遇到非法的端口或不是 32 位十六进制的 token 是**回落到默认值**，而不是把非法值留着 —— 留着一个错的会让下一次启动 listen 失败或路由全 404；
- 端口故意不选 `0`（让系统分配）：每次启动一个新端口，等于每次都是一台新服务器。

**三、token 是路径的第一段，对不上就 404，什么都不转发。**

`/${token}` 之外的任何路径都得到 `404 没有这个地址`，请求不会被转发、配置的头不会被用上。这是转发器唯一的授权：本机任何进程都可能来试这个端口（`127.0.0.1` 不是权限边界），32 位十六进制 token 是那条边界。

**四、头的合并顺序与同步那边一致，只有 `authorization` 例外。**

配置的头先写入，**客户端自带的头覆盖它** —— 客户端的协议头必须赢（`content-type`、`depth`、`if-match` 手一滑就换了一种语义）。唯一的例外是 `authorization`：配置里给了就用配置的，因为「配置里给了自己的授权」意味着用户要的是那份令牌（Bearer 之类），而客户端凭自己的字段拼出来的 Basic 用的是**另一个账号**。

`host` 单独丢弃并改写为目标地址的 host —— 转发给真实服务器时 `Host: 127.0.0.1:3426` 是错的。

**五、响应头去掉逐跳头，`Location` 改回转发地址。**

`connection`、`keep-alive`、`proxy-authenticate`、`proxy-authorization`、`te`、`trailer`、`transfer-encoding`、`upgrade` 不转发：这些描述的是「这一段连接」，而不是「这个响应」。不删会让客户端按上游连接的状态去理解自己这一段（例如以为响应体是分块的却不是）。

`Location` 若指向上游的 `origin + basePath` 前缀，就换成转发地址；纯路径且以 `basePath` 开头的同样处理。不重写的话，客户端会在下一个请求里绕过转发器直接去访问真实服务器 —— 那边没有 token、也没有配置的头，于是得到一个 401，而用户完全看不出为什么。

**六、转发与同步彻底分开：自己的文件、自己的路由、自己的卡片小节。**

- 文件：`<profileDir>/.dsh-webdav-relay/relay.json`（`0600`，目录 `0700`），**不在** `.dsh-webdav-sync/` 里，也**不是**一份、不进备份。转发器的配置跟着这台电脑走，没有理由跟着备份跑到别的机器上。
- 路由：`/plugin/webdav-relay/status` 与 `/plugin/webdav-relay/config`，与同步的 `/plugin/webdav-sync/*` 平行，互不调用。
- 界面：同一张卡片底部一个独立小节，自己的「保存」，与同步的「保存」互不影响 —— 改转发器的端口不该让同步那份草稿变成「未保存」。
- 生命周期：`ctx.effect` 在插件卸载时 `stop()`；`bind()` 在每次 `status()`/`save()` 之前比对文件路径，`profileDir` 变了就重读重建套接字（与引擎读配置同一个模式）。

被否决的备选：**让转发器的配置成为同步的一份** —— 它描述的是「这台电脑上有一个客户端正从这个端口拿东西」，不是「所有电脑应该一样的设置」；同步一份端口，两台电脑就会互相覆盖对方的端口。

## 影响

- **正面**：任何 WebDAV 客户端都能用上这份账号与额外请求头，客户端那边只需要填一个地址（不需要账号密码，也不需要头）。magpie 的 `internal/davsync` 因此能落到同一台服务器上，且与本插件的备份文件互不干扰（`dsh-webdav/dsh-profile.prop` 与 magpie 自己的文件夹各自安好）。
- **正面**：转发器不做 WebDAV 语义，所以 `PROPFIND`/`MKCOL`/条件写入/大文件上传全都按客户端的实现照常工作，本插件这边没有一份需要跟着 WebDAV 版本演的代码。
- **负面：DSH 必须开着。** 客户端连的是本机进程，Host 退出转发就断了。这是这个方案唯一的结构性代价，也是它换来的东西（凭据不外发、头只在一处维护）的对价。
- **负面：凭据对「本机上读得到那个地址的进程」开放。** 收敛点是那 32 位 token 与只绑回环；但一个有本机文件读取权限的进程可以读到 `relay.json`（`0600`，但仍然是你这个账号可读的），于是也能用这些凭据。它不比为「把密码写在客户端配置里」更差，也没有更好。
- **负面：多了一个常驻监听的端口。** 默认 `3426` 被占用时不会崩，`status` 会带着 `error` 说端口用不了（`EADDRINUSE` 不抛），卡片上照实显示；但这意味着用户得自己换一个端口，而换端口就等于给客户端换一台服务器（见决策二）。
- **行为不变**：同步的配置、状态、合并算法、备份格式一个字节都没改；转发器不读 `sync.json`，也不碰 `sync-state.json`。关掉转发器（`enabled: false`）只是不监听，配置原样留着。
