# 0036 第五份：附加目录，路径跟着配置走，恢复写回同一个目录

- 状态：已接受
- 日期：2026-10-19

## 背景

用户 2026-10-19 的需求（原话：「在同步内容标题后增加一个新增按钮，可以指定目录同步，恢复时也恢复到相同的目录下」）。原来的四份（[0005](0005-four-parts-and-plugin-exception.md)）都切自 profile 的两份文件：`cordis.patch.yml` 与 `package.json`。用户手上还有别的东西想跟着走 —— 一个放笔记、放 agent 提示词、放脚本的目录 —— 它既不在 profile 里，也不适合塞进 patch 行。

难点不在「读一个目录」，而在这个功能可能造成的**唯一一种无法挽回的事故**：把用户自己目录里的文件删掉。四份里 `patch` 的删除会传播（另一台删了一行，这里也删那一行），是因为那一行随时可以从 `sync/` 的留档里找回来；一个人的笔记目录不行，那里面没有「留档」这回事。

## 决策

**加第五份 `dirs`，值是「目录的绝对路径 + 目录里的文件」**（`src/wire.ts`）：

```ts
export const PARTS = ['models', 'defaults', 'plugins', 'patch', 'dirs'] as const

export interface DirSpec {
  path: string                 // 命名它的那台电脑上的绝对路径，原样带走
  files: DirFileSpec[]         // { path: '相对/路径', data: base64 }
}
export interface DirsPart { dirs: DirSpec[] }
```

**路径是数据的一部分**，这也是需求的后半句：`writeDirs` 按 `path` 写回同一个目录，而不是在第二台电脑上另造一个。跨机器的路径在这台电脑上可能没有意义 —— 相对路径、盘符不存在、没有权限 —— 这类路径**不读也不写**，但条目原样留在 part 里（丢掉它等于替那台电脑删了它）。

**写入只增不减。** 同步会写、会覆盖，永不移除。在一台电脑上删掉的文件会从别处回来；要在所有电脑上删掉，手动删。这跟插件清单的取舍是同一条（[0005](0005-four-parts-and-plugin-exception.md)）：镜像删除是唯一一种事后说不清、也补不回来的操作，而「删了又回来」只是烦人。相应地，`applied.dirs = null`（别的电脑把这一份拿掉了）在这里**什么都不做** —— 其余四份靠它删行，这一份没有行可删。

**读不出来不等于空目录。** 一个目录被删了、盘没挂上、没权限，`readDirs` 把它记进 `problems`（`DirProblem`），`dirsPartOf` 用**服务器上的那一份原样顶替**这次读取：

```ts
// src/dirs.ts — 读失败的那些目录取服务器上的副本，其余照读
const entry = fromDisk.get(path) ?? fromServer.get(path)
```

否则「读不出来」会被读成「这个目录里一个文件都没有」，下一次推上去就是**替所有人删掉了整个目录**。`DirProblem.missing` 再区分「只是不在这台电脑上」（恢复可以建它）与「读不了」（绝不盲写），`writeDirs` 的 `skip` 集合就是后者。

**有上限，且整目录为单位。** 每份配置最多 `DIRS_MAX = 5` 个目录、每个目录最多 2000 个文件 / 8 MiB（base64 之前）。超了**整个目录**不同步并报出来，而不是带一半：一半目录推上去，等于替别人删了另一半。跳过 `node_modules` 与 `.git`（各自的依赖与仓库有自己的主人），不跟随符号链接（会走出目录或绕圈）。

**空列表与缺席不是一回事。** 一个没指定目录、服务器上也没有的电脑**不写这一份**（不是推一个 `{dirs: []}` 上去），否则它会替指定了目录的电脑把列表清空。反过来，指定过目录的电脑把列表清空，表示「这台不再同步它们」：part 原样留在服务器上，文件一个不动，另一台电脑照旧在它们之间同步。

**拿掉的那一份不服从删除。** 如果 part 在服务器上消失了（比如旧版本写出的包），而这台电脑仍然指定着目录，这台电脑把自己的副本推回去 —— 文件本来就在这里，part 不过是在说「哪些路径要跟着走」。

**卡片的入口放在「同步内容」标题行右侧**：标题 + `新增` 按钮（`css.legendRow`），下面是每行一个绝对路径输入框 + `移除`，到 5 个时按钮变灰。`dirs` 这一份**没有复选框**（`isToggledPart` 把它排除在外）：列表本身就是开关，空列表就是「这台不同步」，再加一个 flag 会让「列表为空但 flag 为真」这类矛盾状态出现（`syncsPart` 里写了同样的理由）。读不出来的目录按「哪一条路径、为什么」直接列在列表下方。

**留档只在真要写文件时封。** `dirsDiffer` 先按盘上的字节比一遍，只有确实会改动文件才 `keepBefore`：一个被别的电脑塞过来的大目录，若每次同步都封一份，`sync/` 会以每次几兆的速度长大，而那次同步一个字节都没改。

被否决的备选：

- **镜像删除（同步也删）。** 直接违背上面那段背景：一次误删、一次盘没挂上、一次「我刚整理过」，就是别人目录里的文件消失。留档救不了它。
- **每台电脑各用各的路径**（服务器上只放相对结构，落地路径由本机配置）。需求明说「恢复到相同的目录下」，而且多一个「路径映射表」的配置面，等于让用户在两处维护同一件事。
- **`dirs` 也加一个同步开关。** 见上：列表即开关。两种说法迟早会不一致 —— 那时卡片显示「关」，part 却照旧被带走。
- **整目录塞进 `patch` 份**（当作一行 YAML）。文件内容要多一层转义、注释与缩进的合并逻辑，而且会把 8 MiB 的 base64 挤进一个靠 YAML 文档级合并维护的文件里。
- **超过上限时截断着带**。见上：半个目录比不带更危险。

## 影响

正面：

- 需求的两半都成立：能指定目录，能在任何一台电脑上恢复到**同一个路径**。
- 「删不掉」这条规则让这个功能的最坏结果只是「文件又回来了」，而不是「文件没了」。
- 服务器上仍然只有一个密文文件；`dirs` 的内容和其余四份一样封在里面，服务器看不到路径与内容。
- 读失败被当成「不知道」而不是「空」，与 [0027](0027-damaged-is-not-missing.md) 同一条原则。

负面：

- **包体会变大**：base64 有 4/3 膨胀，再加 AES-GCM 的开销；8 MiB 的目录封完约 11 MiB，而目前是每次整体 PUT，没有增量。上限就是为了让它有界。
- **冲突仍按「整份较新的胜」**处理，不做目录级三方合并：两个人同时改同一个目录里的不同文件，只有较新的那份整体生效，另一份进 `sync/` 留档（与其余四份同规则）。真要细到文件级，得给这一份单写一套合并，代价与收益不成比例。
- **5 个目录 / 8 MiB 是硬上限**，超了只能拆成几次同步或换别的方式带走。
- **`node_modules`、`.git`、符号链接被静默跳过**：文档写了，但用户从卡片上看不到「这个目录里有东西没被带走」。
- 空列表的语义偏隐晦：把最后一个目录移除，只是「这台不再同步」，服务器上那份不会消失，别人仍在同步它。卡片此时不显示这一行（只留 `新增` 按钮），说得不够直白。
