# 0026 换密码不换身份，所以不重置基线

- 状态：已接受（否决了审查提出的改法）
- 日期：2026-10-16

## 背景

`stateKey()` 是本地状态的隔离键，由地址、用户和口令三项哈希而成（ADR 0011）。任何一项变了，本机记录的基线就作废，下次同步被当成第一次加入。

审查提出密码也算身份，应该进 `stateKey()`。理由是：换过密码之后，同一份基线可能已经不再对应服务器上的东西。

## 决策

密码**不**进 `stateKey()`。理由有三层。

第一，密码在这里的角色和地址不同。地址和用户决定"我连的是谁的文件夹"——换了就是另一个文件夹，基线完全不相干。口令决定的是"我怎么打开这个文件夹里的文件"，密码决定的是"服务器认不认我"。服务器换了密码，文件夹还是同一个文件夹，里面还是同一份内容。把钥匙的更换当成房间的更换，等于主动丢掉一份还能用的基线。

第二，后果不对称，而且很糟。基线一旦作废，本机下一次同步就会按首次加入处理：所有分片都算服务器赢，本机的编辑被接管——正是 ADR 0024 花力气才让它变成"有副本、有通知"的那件事。而服务器侧换密码根本不会改动内容，不该触发这个。

第三，配置接口本身就常改密码。用户换密码时填的是同一个地址、同一个用户，插件没有任何理由怀疑服务器上的文件换了一份。

## 影响

正面：改密码不丢基线，不触发服务器接管。

负面：改密码之后插件不会主动去核对服务器上的文件有没有同时被人改过。第一次同步会读服务器并把差异记下来，用户能看见；如果他同时改了内容，走的是正常的三方合并而不是"全盘接管"。这是可以接受的交换。

同时修正 ADR 0011 里那句不准确的注释——原文写"任何一项变化都会重置状态"，会被读成密码也算在内。

被否决的备选：
- **把密码进 `stateKey()`**（审查的提议）。会因轮换凭据而触发全盘接管，见上文第二点。
- **改密码时清空基线但保留通知**。同样触发接管，只是换了种说法。
- **记住旧密码直到下一次同步成功**。要把密码的历史存下来，ADR 0019 刚刚才把"不记住密码"做成一个可信的承诺。
