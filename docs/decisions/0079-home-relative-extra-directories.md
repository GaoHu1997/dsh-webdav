# 0079 — 附加目录支持 `~` 前缀，按每台电脑自己的 DSH 主目录解析

- 状态：`已接受`

## 背景

用户在多台电脑之间同步时发现：已存在供应商的 API 地址、模型列表、供应商列表排序、模型列表排序，在另一台电脑上始终不更新。排查结论是这四样**根本不在已同步的份数里**：

- 供应商 API 地址（按协议族的 `endpoints`）、多密钥清单（每把钥匙的 `ref`/`alias`/`models` 范围）、余额地址等，由 `dsh-model-think-level` 插件写在自己名下的目录 `$DSH_HOME/dsh-model-think-level/`（`key-index.json`、`key-serves.json` 等），不进 `cordis.patch.yml`；
- 供应商列表排序、每供应商的模型列表排序、供应商启用开关，存在**浏览器 localStorage**（`dsh-model-think-level.provider-order` 等），宿主侧根本没有文件；
- 多密钥的**值**（`WB_API_KEY_2` 这类）只被 `key-index.json` 点名，而 `keys` 份的引用收集只扫 profile 文件的 `apiKeyEnv`/`secretEnv`，所以值也不旅行。

「附加目录」（0036）本来是同步 `$DSH_HOME/dsh-model-think-level/` 的现成载体，但它的路径按**绝对路径字符串**跨机器匹配：`C:\Users\gaohu\.dsh\...` 到了另一台机器（用户名不同、或干脆是别的系统）只是一个对不上的死路径——两台机器各带各的份、各写各的盘，永不合并。被否决的备选：

- **手改两台机器的绝对路径一致**：多数做不到（用户名不同），Windows 与 POSIX 更不可能。
- **在 bundle 里加一个「插件目录」新份数**：为某一台插件硬编码 wire 格式，`dirs` 份加上 home 相对语义后是通用的，不需要新格式。
- **整份凭据文件 `.credentials.yaml` 当目录同步**：绕过凭据服务的逐引用合并，两台各自加过钥匙时整文件冲突、新者胜，正好丢一边的钥匙——`keys` 份的 union（0077）就是为避免这个才存在的。

## 决策

一、`~` 开头的附加目录路径**按字面旅行、按机器解析**（src/dirs.ts）。

- `homeRelative`：路径是 `~` 或 `~` 后跟分隔符（`~/x`、`~\x`）。`~user` 不算——那是 shell 里别的账户的家，在这里只当普通相对路径拒绝。
- `expandHome(path, home)`：普通路径原样返回；`~` 路径解析到调用方给的 **DSH 主目录**（`$DSH_HOME`，缺省 `~/.dsh`），不是 OS 主目录——本插件的整个世界就是 DSH 主目录，要同步的插件数据（`dsh-model-think-level/`、`skills/`）都在它名下，`$DSH_HOME` 被改过别处时依然正确，而且用户不用写 `.dsh` 那一段。
- `readDirs`/`writeDirs`/`dirsDiffer` 增加 `home` 参数（`ResolvedPaths.homeDir`，与 `homePatchFile` 同一条「没有就说没有」的规矩）：`~/dsh-model-think-level` 在 A 机读 A 的、在 B 机写 B 的，而份里携带的 `path` 永远是字面 `~/dsh-model-think-level`，于是两台机器在份里是**同一个目录**，三方合并正常工作。
- 解析不出主目录的机器报 problem（`missing` 不置位——不是「不在」，是「说不出在哪」），服务器那份原样穿行，什么都不写、什么都不删，与普通相对路径的既有待遇一致。

二、跨版本与旧配置安全。旧版本读到 `~/x` 视为「不是本机绝对路径」原样携带、不写不删（0036 的既有规则），所以一台升级一台没升级时目录内容不会丢，只是不合并；`normaliseDirs` 排序对 `~/` 与绝对路径一视同仁，两台机器对同一集合的哈希仍然一致。

三、同步目录里的 JSON 文件贡献凭据引用（src/keys.ts `dirRefs`）。约定只有一个词：文件名以 `.json` 结尾、字段名恰为 `ref` 的非空字符串值，收集起来并入 `readKeys` 的名字列表。`dsh-model-think-level` 的 `key-index.json` 用 `ref` 字段列出它路由的每把钥匙，其中多数 profile 从不点名——没有这条，目录把**名字**带过去了，**值**还留在原机器。容错与代价：非 JSON、无 `ref`、空值都贡献零；一个解析不到值的名字只是白查一次（`readKeys` 对无名分的既有规则），误报无副作用。

四、卡片文案说清 `~` 的语义（按每台电脑的 DSH 主目录解析、举例 `~/dsh-model-think-level`），输入框占位与提示同步更新；配置保存处放行 `~/` 前缀、继续拒绝其余相对路径。

## 影响

- 附加目录从此有两类路径：绝对路径（路径本身旅行，适合两边都一样的盘符/挂载）与 `~` 相对路径（名字旅行、各家解析，适合 DSH 主目录下的插件数据）。
- 用户的完整操作是：在两台机器的附加目录里都填 `~/dsh-model-think-level`。此后 `key-index.json`（API 地址、多密钥范围、别名）、`key-serves.json`、以及将来任何落在该目录的插件状态都随同步走；多密钥的值随 `keys` 份走（0077 的 union 语义不变）。
- 供应商列表排序与模型列表排序仍不随行：它们只在浏览器 localStorage 里，宿主侧无文件可同步。方案是 `dsh-model-think-level` 把这三项偏好镜像到自己的目录（如 `ui-preferences.json`）并在启动时回读——镜像落盘后由本决策自动携带，不需要本插件再做任何事。
- 上限不变（每目录 2000 文件 / 8 MiB，跳过 `node_modules`/`.git`）。一个超限目录整份拒绝并报 problem，不会半携带（0036 的既有取舍）。
- 测试 +18：dirs 单测（识别/展开/读/写/比较/无法解析）、keys 单测（`dirRefs` 的收集与容错）、宿主配置（`~/` 收下、`~user` 拒绝），以及 `tests/two-machines.spec.ts` 6 条双机端到端（已有供应商的地址/模型/双侧排序改动到对面、同内容重写不挡路、不同主目录名的两台机器合一个 `~/` 目录、钥匙值随行、解析不出主目录的机器穿行不落盘）；另以用户真实 861 行目录做过一次同流程人工核验。
