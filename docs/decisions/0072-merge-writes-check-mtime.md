# 0072 合并写回前复验文件 mtime，别的程序改过的文件不写

- 状态：已接受
- 日期：2026-10-24

## 背景

一次同步是「读快照 → 决定 → 封装上传 → 写回本机」。读快照（`take()`）与写回（`applyMerged()` → `writeIfChanged()`）之间隔着两次 PBKDF2（600 000 轮）和一次完整网络上传，窗口在慢网络上是秒级。这期间 DSH 宿主自己可能写同一个文件——用户在界面上改模型目录、装插件，宿主就写 `cordis.patch.yml` / `package.json`。

`writeIfChanged()` 只比较**字节**。合并产物与磁盘内容不同就整文件覆盖，宿主在窗口里写下的那次编辑不在合并的任何一边：快照没读过它，服务器上没有它，`sync/` 里为 Undo 留的副本封存的是快照。这次编辑就真丢了——不是同步语义里的"一边赢"，是无声丢失。

`serially` 队列（0018）只串行化本插件自己的操作；ETag 只保护服务器端的文件。本机文件此前没有任何保护。

自动同步（3 分钟档）会周期性地打开这个窗口，所以这不是"两次按键恰好撞上"的奇景。

## 决策

**合并写回前，对每个要写的文件 `stat` 一次，mtime 与快照读到的不同就拒绝写**（`refuseIfMoved()`，在 `applyMerged()` 的三个写点之前各一次：profile patch、模型目录所在的 home patch、package.json）。报错文案让下一次同步读作"再同步一次"：服务器上的文件不受影响，下次同步会把两边改动合并——外部编辑的 mtime 更新，冲突裁决会站在它那边。

只有**合并**受此限制。`restore`、`undo`、`importBackup` 传 `overwrite`：它们是"把手上这份盖过去"的显式指令，文件在期间变了正是它们要盖的对象；为这些路径留档的副本取自当下的磁盘，不是旧快照。

否决的备选：

- **写前重读文件、按内容合并**：等于把三方合并变成四方，复杂度不成比例，且宿主写的格式（注释、排版）无处获取合并规则。
- **文件锁 / 跨进程锁**：宿主不持锁，锁只拦得住自己。
- **只对 package.json 生效**：patch 文件承载模型目录，是用户编辑最频繁的一个，恰恰最需要。

## 影响

- 好的一面：快照与写回之间的外部写入不再被覆盖；被拒的那次同步在状态里留下一条可读的错误，下次同步自动收敛。
- 代价一：宿主恰好在写回前一瞬写文件的同步会失败一次，需要再同步一次；窗口是毫秒级，实际撞上的概率低，且失败无副作用（服务器文件已写，下次同步按 changed-there 收敛回来）。
- 代价二：mtime 是见证不是证明——外部程序在同一 mtime 粒度内先写后还原的极端情形看不见；反过来，只改 mtime 不改内容的工具（touch）会造成一次多余的拒绝。都可接受。
- 附加目录（`dirs` 分片）的写回**不**在此列：`writeDirs` 逐文件比对内容、从不删除既有文件，语义本就是并行的。
